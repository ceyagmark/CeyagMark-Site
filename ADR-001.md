# ADR-001 — CeyagMark Next.js rebuild architecture

Status: accepted. Written before the first scaffold command, per fable-web W1.
Session: unattended build, 2026-08-25. Kickoff: `Projects/CeyagMark/KICKOFF-NEXTJS.md`.

## Context

ceyagmark.com is a static HTML site on HostArmada/LiteSpeed, deployed by manual cPanel
upload. An ad-readiness audit (2026-08-22, see memory `ceyagmark-nextjs-rebuild`) found
the lead capture structurally broken: `/contact` discards submissions behind an undefined
endpoint and shows success anyway, `/quiz`'s endpoint is commented out, GTM fires zero
tags, and there is no privacy policy. Shashika decided to rebuild as a real application
rather than patch the static stack. This ADR is the seed the kickoff prompt asked for;
numbers below are filled from the actual planning docs and the PPI precedent, not
placeholders.

## Decisions

1. **Next.js 16 App Router + React 19 + TypeScript (strict) + Tailwind 4.** Matches the
   PPI precedent, gives ISR for the SEO-critical marketing pages and a real API surface
   for the booking engine. `no-explicit-any` and `no-unchecked-indexed-access` enforced in
   `tsconfig.json`.

2. **Route classes:**
   - **Static/ISR:** all marketing pages (`/`, `/services`, `/consulting`, `/approach`,
     `/portfolio`, `/case-*`, `/about`, `/contact`, `/growth-audit`, `/quiz`, `/free-audit`,
     `/built-by`, `/privacy`, `/terms`). They change rarely and every one of them is a
     ranked page — SEO parity requires them servable without a request-time DB hit once
     content stabilizes.
   - **Dynamic (`force-dynamic` or route handlers):** `/book/*` (reads live availability),
     `/admin/*` (reads live bookings/leads, requires auth), and every route under `/api/*`.
     Reason named per W1: these read state that changes between requests and must never be
     cached to an old page.

3. **One deployable unit.** The whole app (marketing, booking, admin, API) ships as one
   Next.js app on one Vercel project. No second service — nothing here has a scaling or
   team reason to split.

4. **Data: Supabase Postgres, two sources behind one port.** `local-source.ts` (PGlite,
   dev/test) and `supabase-source.ts` (production), both implementing the same
   `DataSource` interface. BUILD-NOTES.md from PPI records this drifting four separate
   times — every schema change updates both files in the same commit, checked by
   `scripts/check-migrations.mjs` (ported from PPI).

5. **Money as integer minor units.** Cents (LKR: 100ths of a rupee is unconventional, so
   LKR prices are also stored as integer minor units — smallest unit = 1, i.e. whole rupees
   stored as integers with no decimal; this matches how the existing site already quotes
   LKR prices as whole numbers: 14999, 30000, 39900, 3000). USD stored as integer cents.
   Never `parseFloat` a price anywhere, client or server (PPI's float-money bug, BUILD-NOTES
   Slice 4).

6. **Timestamps `timestamptz`, stored UTC.** Display timezone is **Asia/Colombo
   (UTC+5:30)**, applied only at render/format time via `Intl.DateTimeFormat` with
   `timeZone: 'Asia/Colombo'`, named once here so it is never hardcoded as an offset.

7. **Server owns truth (W6).** Availability, pricing, and booking state transitions are
   computed server-side in a single Postgres function (`create_booking`), mirroring PPI.
   The client renders and predicts (optimistic slot removal); the server recomputes and can
   overrule.

8. **One error envelope (W9).** Every API route returns either the success shape or
   `{ error: { code, message, details? } }`. No stack traces or framework HTML on any
   `/api/*` response — enforced by a shared `apiError()` helper and a route-level try/catch
   convention.

9. **Contract before implementation (W8).** `SLICE-0-CONTRACTS.md` in this repo lists every
   endpoint, its method, request/response shape and error codes, written before Slice 1
   code.

10. **Notification port, two adapters** (copied from PPI, and from the kickoff spec): a
    `ConsoleNotifier` (always available, prints and logs `skipped`) and a `ResendNotifier`
    (real, selected when `NOTIFY_FROM_EMAIL` is set). Every send — successful, skipped, or
    failed — writes one row to `notification_log` with an explicit status. No adapter ever
    reports `ok: true` for a send that did not leave the process.

11. **Lead sink port, three adapters:** DB (always on, source of truth), Hub (HTTP POST to
    `HUB_INTAKE_URL`, env-gated, logs `skipped` when unset), File (appends to
    `data/hub-pipeline-log.jsonl` inside this repo, never into `Agency/` — that tree is
    frozen until 2026-08-29 per `Agency/baseline-week.md`).

12. **Motion: `motion/react` + CSS**, per the kickoff decision, overriding this workspace's
    GSAP default for this project (same override PPI made, weighing bundle cost against a
    genuinely idiomatic React animation API for a component-heavy app — unlike PPI's
    static HTML, this is React throughout, so `motion/react` composes with components
    instead of fighting them).

13. **Deploy target: Vercel preview URL only.** No `vercel --prod`, no `vercel --yes`
    unlinked (PPI incident: a stray project got created that way). If the Vercel CLI is
    unauthenticated in this environment, the app ships deploy-ready with written
    instructions in `DEPLOY.md` instead of an actual deploy attempt.

## Performance budget (F4 — numbers, not adjectives, per fable-thinking §5)

| Metric | Budget | Why this number |
|---|---|---|
| LCP | ≤ 2.5s on simulated Slow 4G | Core Web Vitals "good" threshold |
| CLS | ≤ 0.1 | Core Web Vitals "good" threshold |
| INP | ≤ 200ms | Core Web Vitals "good" threshold |
| JS shipped per marketing page | ≤ 170KB gzipped | PPI's hero shipped 52KB for one image; a component-heavy React app needs more headroom than PPI's static HTML, but Motion + React runtime must not approach the old site's near-zero JS baseline without a stated reason |
| Homepage hero image | ≤ 120KB WebP at first-viewport width | PPI's hero budget, reused — same connection-quality assumption (a buyer or visitor on Sri Lankan mobile data) |
| Total page weight (marketing) | ≤ 900KB transferred | Room for fonts + one hero image + JS budget above, still well under a 3G-hostile 2MB |

Measured at Slice 4 (motion layer) and Slice 5 (hardening) gates, per-page, saved to
`evidence/`.

## Consequences

- Two data sources must be kept in lockstep by discipline, not by tooling — this is the
  single highest-recurrence defect class in the PPI build (four occurrences). Every
  migration PR touches both files or is incomplete.
- Marketing pages being static/ISR while lead-capture forms on those same pages POST to
  dynamic API routes means every page is a hybrid: statically rendered shell, dynamically
  handled mutation. This is deliberate and standard App Router shape, not a compromise.
- No payment gateway and no WhatsApp Business API means the booking engine's "confirmed"
  state is not gated on any external payment truth — a booking is confirmed the moment the
  server accepts it, same as PPI's no-deposit policy, and money changes hands out of band.
